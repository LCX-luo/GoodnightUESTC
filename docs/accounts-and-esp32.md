# 多账号授权与 ESP32 接续

当前入口：http://127.0.0.1:8090/accounts 。仅本机服务，不是可以双击独立运行的静态 HTML。必须通过本机服务使用，不能把 HTML 和凭据文件发给别人替代本人授权。

## 从零准备

1. 添加账号备注；每个配置的目录使用随机 ID，不使用学号作为目录名。
   也可点击“导入当前电脑已保存的账号”，将现有学校会话、微信凭据和位置重新加密到独立配置；不复制旧操作票据，不联网提交，重复导入会选中已有配置。
2. 在该配置输入本人学校账号密码并打开 Edge，完成正常验证。密码不保存；学校 Cookie 加密保存。
3. 用绑定该学校账号的本人微信扫码。后端核对浏览器与小程序身份一致，才签发票据；微信凭据独立加密保存。
4. 使用与首页一致的地图选择本人实际位置、坐标系并保存。可运行只读检查，不会提交签到。
5. 点击“保存添加到库”，资料完整且身份验证通过后才出现在顶部列表；选择已有账号可重新登录更新。
5. 切换到下一个配置，重复完成。微信本人授权和学校身份核对不能跳过。

各配置的会话、微信凭据、位置、加密密钥和 CSRF Cookie 独立。页面不显示 code、Cookie、token 或票据，不提供签到接口。配置索引只含随机 ID 和备注；敏感资料位于被 Git 忽略的 private-data/profiles，不能上传。

账号记录表显示学号、是否保存学校会话/微信凭据/位置，以及今后成功取票时记录的验证时间。保存状态不代表当前有效；旧凭据没有验证时间记录时需重新验证，不伪造历史时间。

## 设备信息证据

用户指定旧项目 `C:/Espressif/frameworks/esp-idf-v5.1.2/examples/control`。其 sdkconfig 设置 IDF_TARGET=esp32、Flash=2MB、未启用 SPIRAM；README 也标注普通 ESP32 和 ESP-IDF 5.1.2。这是构建配置，不是读取芯片所得的实物容量，不能据此断言开发板实际只有 2MB。

之后用户连接实物并授权只读识别。COM4 为 CP210x；首次因启动模式不符失败，由用户手动进入 BOOT 后使用现有 esptool 的 ROM/no-stub 模式读取成功：ESP32-D0WD-V3，revision v3.1，双核 240MHz，40MHz 晶振，实际 Flash 4MB。没有刷写 Flash、替换固件或改动旧空调工程。工具会复位开发板，用户松开 BOOT 并按 EN 可恢复原应用。

4MB 为实物读取结果，覆盖此前“配置为 2MB”的容量推测，但仍未确认 PSRAM、可用堆内存和分区。该板可作为移植验证目标，不能仅凭 Flash 容量认定完整微信协议与多账号无人值守已可运行。Python 3.13 SDK 不能直接复制到此 ESP32 运行；需要 C/C++ 移植和实际内存峰值测试。

## 每日 21:10 任务的未完成环节

预期流程是北京时间同步时钟 → 独立读取一个账号 → 刷新该账号微信凭据 → 原生协议获取新 code → 建立小程序会话并核对账号 → 第二个新 code 换票 → 读取当天记录/时段/实际位置条件 → 单次提交 → 回查。每个账号分别执行，失败不影响其他账号，也不能盲目重试未知结果。

已开始编写原生取码、独立串口导入和 21:10 调度实验代码，并在隔离副本中与空调任务合并构建；当前尚未完成编译及实物验证，未刷写旧设备。页面的 21:10 是计划时刻，不代表任务已启动。旧项目使用的公开 MQTT 通道不应承载学校或微信认证材料；设备导入方案需单独实现。

现有页面不保存学校密码；CAS 会话到期后可能需要本人重新登录，不能据此承诺永久无人值守。微信 refresh_token 也可能失效。code 和操作票据应每次新取，不固化成长期常量。
